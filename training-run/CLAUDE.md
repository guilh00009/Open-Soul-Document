## how to create good reward functions
it's important that you create good, robust reward functions.

refer to https://castform.com/docs/environments/rewards for how to create good rewards.

when you are using qualitative rubric-based llm judge rewards, try to make the rubrics comparative. this could either mean comparing completion with ground truth. it could also mean using `compute_group_reward` to rank completions as mentioned in https://castform.com/docs/environments/rewards#ranking-instead-of-absolute-scoring.

ensure scores coming out of the reward functions are positive and not negative.

## launching training runs + managing dependencies
refer to https://castform.com/docs/train/launching on how to launch training runs.

make sure to handle dependencies correctly. your environment can have dependencies in two forms: 1. external pypi packages or 2. other files in your project.

these dependencies have to be bundled in when you call `upload_training_run`, specifically:
- all the external pypi packages you rely on should be passed in through the `pip_dependencies` arg
- if there are local modules/packages you rely on, they should be passed in through the `local_modules` arg. pass the imported module objects directly (e.g. `local_modules=[scoring_utils]`), not their names as strings (`local_modules=["scoring_utils"]`).

example — say your env imports `httpx` (PyPI) and `scoring_utils` (a local file):

```python
# scoring_utils.py
def compare(response: str, ground_truth: str) -> float:
    return 1.0 if ground_truth.strip() in response else 0.0
```

```python
# run.py
import httpx
import scoring_utils

class MyEnv(BaseEnv):
    async def compute_reward(self, rollout_id, messages, task=None, **kwargs):
        text = extract_completion_text(messages)
        score = scoring_utils.compare(text, (task or {}).get("ground_truth", ""))
        return {"quality": score}

uploaded = upload_training_run(
    env_class=MyEnv,
    train_dataset=train_data,
    eval_dataset=eval_data,
    run_name="my-run",
    constructor_args={},
    pip_dependencies=["httpx"],
    local_modules=[scoring_utils],
)
```

## validation before submitting training runs
before submitting training runs, it's important that you run the `validate_env` function to make sure that things generally work, so gpu compute isn't wasted.
refer to https://castform.com/docs/environments/testing on how to use `validate_env`.

# first party use-cases
if the user's query falls under some of the first-party use-cases the platform supports, the following docs can be useful.
these first party use-cases are search/rag and traces.

search/rag involves post-training an llm to be able to use a search tool (vector search tools, etc.) to search over domain-specific corpora effectively. refer to https://castform.com/docs/rag/guide/ on how this can be done. if the developer already has an existing vector db, you can look at how to integrate with that here: https://castform.com/docs/rag/integrations/

the other first party use-case is using existing agent traces/observability data a developer has collected from a production agent. refer to https://castform.com/docs/traces/overview/ on how to support this. there are some existing integrations built out to some observability tools -> but if not, you might have to build one yourself.
